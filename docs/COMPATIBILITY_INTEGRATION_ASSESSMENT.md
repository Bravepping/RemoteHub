## 当前路线的真实兼容边界

当前主链路为 Rust DXGI/MF → H.264 RTP/SRTP → 标准 WebRTC PeerConnection → WebView2，信令为临时认证WSS、控制为control.v1 DataChannel。Sunshine/Moonlight上游生态在原基线中是另一套串流/配对/控制协议；Foundation/V+是否含额外私有扩展须核验。

| 层 | 现有 RemoteHub | 拟对接目标 | 集成含义 |
| --- | --- | --- | --- |
| 桌面体验 | Tauri/Rust/Vue/TS，一套可见UI；WebView2自身有子进程 | 统一管理三件套能力 | 一个安装包/可见客户端可以管理多个后端进程，但这需要明确例外和生命周期控制，不等于当前单产品主程序基线已满足。 |
| 配对/会话 | 实验一次性码、HMAC、短票、原生同意；非正式长期身份 | 目标主机/客户端原生配对、证书及权限 | 不能把RemoteHub短票当成Moonlight原生配对凭据；须单独验证目标配对并纳入统一撤销/停止。 |
| 媒体/控制 | SDP/ICE/DTLS/SRTP/SCTP + H.264 | 目标生态的串流握手、包化、解码与输入 | 共享H.264不代表包、会话或控制兼容；WebView2 video不能直接当作任意目标串流客户端。 |
| 网络承载 | 已批准候选、ICE选路、coturn UDP | EasyTier覆盖网络及其实际选路 | 覆盖网可以承载已支持的IP协议，不能完成媒体协议翻译；现有TURN也不能凭配置直接转发另一套串流协议。 |
| 呈现 | WebView2/WebRTC解码显示 | 受管理V+窗口，或经核验的原生解码/呈现内核 | 是否可嵌入同一会话窗、DPI/焦点/纹理/线程生命周期均需原型。不能假定V+支持无头或嵌入API。 |
| 统计 | WebRTC真实selected pair、帧/ACK/回收 | 各后端真实连接/传输/渲染数据 | 不把EasyTier进程运行写成P2P成功，也不把目标后端的路径冒充WebRTC selected pair；不可得项标unavailable。 |

## 备选集成方案

| 方案 | 能满足的目标 | 代价/风险 | 建议与重估条件 |
| --- | --- | --- | --- |
| A 继续WebRTC默认后端 | 复用已实测媒体/模拟控制/授权，保持Tauri统一客户端 | 不自动满足Foundation/V+互操作，也没有成熟三件套性能对照 | 作为当前可用基线保留；UI明确后端身份，不能标“已兼容三件套”。 |
| B 可选受管理兼容后端 | 若目标版本具备可用接口，可由Rust管理Foundation主机、V+接收端，并可选EasyTier承载 | 多进程/配置/原生配对、退出/孤儿进程、升级/许可；外部窗口可能不满足一个可见UI目标 | **最先评估的兼容原型**，先固定目标并验证API/窗口控制。需要多进程及安装范围批准；若无法统一窗口或安全停止，不默认上线。 |
| C 嵌入/派生兼容核心 | 在接口/许可可行时提供单UI原生接收/主机能力 | 特定内核ABI未知；可能涉及C++/Qt/解码库、FFI线程/崩溃隔离和长期上游合并 | 仅当B无法满足单UI目标且核验核心可复用时原型；不承诺工期更小或当前即可链接。 |
| D 从零写兼容协议 | 理论上保留Rust主进程并实现生态互操作 | 必须承担完整协商/加密/输入/扩展兼容测试；目前无目标协议合同 | 当前不采用；只有明确强制兼容范围且B/C不可行、维护成本经审查后重估。 |
| E 给WebRTC加EasyTier承载 | 可能为特定网络提供显式批准的覆盖网路径 | 不能替代Foundation/V+协议；新增虚拟网卡、路由/驱动权限、节点身份及更大信任面 | 仅在用户确有覆盖网需要、来源/接口核验完成后另立原型；不把它当R06自动修复。 |

推荐 **保留A，先界定B的目标与可行性，C/D/E由明确触发条件再评估**。不是现在同时实现五套后端，也不是承诺最终一定多引擎。当前只有一个已实测后端，没有三方稳定重复需求，故不建设通用插件平台；P1只规划薄能力边界和不可用状态。

## 拟议接入边界（尚未实现）

Tauri/Vue提供同一导航、设备/会话状态与停止入口。Rust拟提供薄Session管理边界，后端选择为“RemoteHub WebRTC”或未来经批准的“兼容后端”，网络承载独立标识“原生网络/未来覆盖网络”。这是设计概念，**没有新增IPC命令或已实现字段**。

- 现有WebRTC后端复用 `hub-webrtc` Session、选路/控制/统计；不复制第二套ICE栈。与兼容后端分别拥有各自的协商/配对，禁止把SDP与目标协议包直接拼接。
- 若采用受管理二进制，只允许固定来源/hash/版本、专用参数与私密工作目录；使用Windows进程组/作业对象等可验证的退出域，停止会话时只回收自己创建的进程，不杀用户原有实例。具体启动参数/API须读目标文档/源码后确定，本轮不臆造命令。
- 单一会话所有者协调采集/编码/呈现；异步回调绑定后端与会话代次，退出后旧结果不得重开资源。失败时回到未连接，不静默切换到另一套不同权限的后端。
- 目标引擎没有WebRTC PC时不能伪造selected pair；必须先设计等价的目标绑定、原生配对/证书、允许端点和权限边界。不能仅用“切换后端”绕过当前授权。现有WebRTC严格ICE校验和P004a本机限制保持。
- EasyTier若未来引入，要独立批准节点身份、特定虚拟接口、确切对端、路由和驱动操作；不自动信任整个私网/覆盖网，不复用LAN网段白名单来放开所有成员。不能假定已有阿里云coturn能当EasyTier中继，不擅自新增云服务。
- 第三方输入/无人值守/音频/剪贴板能力应由权限合同单独控制；P1不因启动目标后端而自动开放这些功能。若无法可靠关闭或限制目标固有能力，该原型不能作为安全集成通过。

强制负例：原生V+连当前纯WebRTC主机、当前WebRTC接收端连纯目标协议主机，不能被UI错误报告为兼容；无批准、版本不符、配对撤销、目标进程失败/退出仍发流、覆盖网其他成员探测须拒绝或明确不可用。不得用普通TCP心跳代替媒体/控制互通。

若用户要求“P1完成后必须直接兼容原生Foundation/V+”，C0/C1及C2原型就是**P1范围决议前置**，不能先把WebRTC外壳做完再宣称该目标完成；若P1只做现有后端的桌面管理，兼容状态必须清晰标为未实现，C0–C5独立留项。

当前路线图：现在完成证据与范围合同；后续仅在Phase0退出及P1/兼容原型分别获批后实施；没有性能证据时不整体迁移、不增加常驻驱动/云节点，也不卸载或停止用户现有三件套。
